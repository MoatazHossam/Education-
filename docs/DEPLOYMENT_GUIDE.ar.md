## 1. التطوير المحلي (بدون Docker)

المتطلبات: Node.js 22 وPostgreSQL 16.

<div dir="ltr">

```bash
npm ci
# Create roles and the database (as a PostgreSQL superuser):
psql -U postgres <<'SQL'
CREATE ROLE midad_owner LOGIN PASSWORD 'dev-owner' NOSUPERUSER NOBYPASSRLS;
CREATE ROLE midad_app  LOGIN PASSWORD 'dev-app'   NOSUPERUSER NOBYPASSRLS;
CREATE DATABASE midad OWNER midad_owner;
SQL
cp .env.example .env     # fill SESSION_SECRET, DATA_ENCRYPTION_KEY, DATABASE_URL, MIGRATION_DATABASE_URL, SANDBOX_WEBHOOK_SECRET
set -a; . ./.env; set +a
npm run db:migrate       # schema + grants for APP_DB_ROLE
npm run db:seed          # plans, 2026/27 catalogue, demo users (prints credentials and the admin TOTP secret)
npm run dev              # http://localhost:3000
npm run dev:worker       # emails (log transport prints them) and billing lifecycle
```

</div>

- `npm run db:migrate` ينشئ بنية قاعدة البيانات ويمنح الصلاحيات للدور المحدد في `APP_DB_ROLE`.
- `npm run db:seed` يضيف الخطط ودليل مناهج 2026/27 ومستخدمين تجريبيين، ويطبع بيانات دخولهم وسر TOTP لمدير المنصة (للتطوير فقط).
- `npm run dev:worker` يرسل رسائل البريد (في بيئة التطوير تُطبع في السجل) ويدير دورة الاشتراكات والفوترة.

الاختبارات: `TEST_PG_ADMIN_URL=postgres://postgres@127.0.0.1:5432/postgres npm test` (تنشئ قواعد بياناتها وأدوارها بنفسها)، و`npm run test:e2e` (Playwright، ويشغّل خادمه الخاص على المنفذ 3100).

## 2. Docker Compose (محليًا أو على خادم واحد)

<div dir="ltr">

```bash
cp .env.docker.example .env.docker   # set every password and secret
docker compose --env-file .env.docker up --build
```

</div>

غيّر كل كلمة مرور وكل سر في <span dir="ltr">`.env.docker`</span> قبل التشغيل. أو استخدم السكربت: `ops/start.sh --env dev` (لينكس) أو `ops\start.bat --env dev` (ويندوز).

الخدمات:
- `postgres`: قاعدة البيانات؛ يُنشئ `deploy/postgres-init/01-roles.sh` أدوارها عند أول تشغيل.
- `migrate`: يعمل مرة واحدة ثم يتوقف: ترحيلات قاعدة البيانات والصلاحيات والخطط ودليل المناهج.
- `app`: التطبيق (على المنفذ `APP_PORT`).
- `worker`: العامل الخلفي (البريد، والاشتراكات، وفحص ملفات الواجبات، والتنبيهات).
- `mailpit`: صندوق بريد للتطوير، واجهته على `127.0.0.1:8025`.

البناء خلف وكيل (proxy) يعترض TLS:
<span dir="ltr">`docker build --network host --build-arg HTTPS_PROXY=… --secret id=build_ca,src=/path/ca.crt .`</span>
(تُستخدم شهادة الوكيل أثناء `npm ci` فقط، ولا تُحفظ في الصورة).

## 3. الإنتاج على خادم واحد (الموصى به للإطلاق)

### 3.1 البنية التحتية

- خادم لينكس افتراضي واحد عليه Docker (مثلًا 2–4 معالجات افتراضية و4–8 جيجابايت ذاكرة). سعر Hetzner CPX22 (معالجان و4 جيجابايت) نحو 7.99 يورو شهريًا بعد تغيير أسعارها في أبريل 2026 ([Better Stack](https://betterstack.com/community/guides/web-servers/digitalocean-vs-hetzner/)). فاحص الفيروسات (ClamAV) وحده يحتاج نحو 1–1.5 جيجابايت من الذاكرة: 4 جيجابايت هي الحد الأدنى معه، و8 جيجابايت تترك مساحة كافية. إن كان يجب أن تبقى بيانات العملاء في مصر أو في المنطقة، فاختر موقع الاستضافة بعد المراجعة القانونية (SECURITY_DESIGN.md §7).
- يُفضَّل **PostgreSQL 16 مُدار** بنسخ احتياطية تلقائية واستعادة إلى نقطة زمنية؛ وإلا فاستخدم خدمة `postgres` المضمّنة مع النسخ الاحتياطي الموصوف أدناه.
- سجل DNS من النوع `A/AAAA` لنطاقك يشير إلى الخادم. المنفذان 80 و443 مفتوحان، ولا شيء غيرهما مكشوف للعموم.
- مزود بريد SMTP (مع SPF وDKIM وDMARC لنطاق المرسل).
- حساب لدى مزود الدفع (Paymob)، أو `BILLING_PROVIDER=disabled` مع فوترة يدوية.

### 3.2 الإعدادات

أنشئ <span dir="ltr">`.env.production`</span> من <span dir="ltr">`.env.docker.example`</span>:

- `NODE_ENV=production`، و<span dir="ltr">`APP_URL=https://<domain>`</span>، و<span dir="ltr">`DOMAIN=<domain>`</span>، و<span dir="ltr">`ACME_EMAIL=<ops email>`</span> (بريد فريق التشغيل).
- أسرار عشوائية قوية، تُولَّد من جديد لكل تثبيت:

  | الإعداد | لينكس | ويندوز (PowerShell) |
  | --- | --- | --- |
  | `SESSION_SECRET` | `openssl rand -base64 48` | <span dir="ltr">`$b = New-Object byte[] 48; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); [Convert]::ToBase64String($b)`</span> |
  | `DATA_ENCRYPTION_KEY` | `openssl rand -base64 32` | الأمر نفسه مع `byte[] 32` |
  | كلمات مرور قاعدة البيانات الأربع | `openssl rand -hex 24` | <span dir="ltr">`$b = New-Object byte[] 24; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); -join ($b \| % { $_.ToString('x2') })`</span> |

  يجب أن تتكون كلمات مرور قاعدة البيانات من حروف وأرقام فقط: فهي توضع داخل عناوين الاتصال بقاعدة البيانات، حيث تُفسدها <span dir="ltr">`/`</span> أو <span dir="ltr">`@`</span> التي قد تظهر في base64.
- `EMAIL_TRANSPORT=smtp`، و`SMTP_URL=smtps://user:pass@smtp.provider:465`، و`EMAIL_FROM`.
- اترك `WEBHOOK_ALLOW_INSECURE_TARGETS` فارغًا: فهو يسمح لإشعارات الأنظمة (webhooks) بالوصول إلى عناوين http وعناوين الشبكات الخاصة، وهو للتطوير فقط، ويرفض التطبيق العمل به في الإنتاج. يرسل العامل الخلفي طلبات HTTPS إلى عناوين إشعارات الأنظمة الخاصة بالعملاء؛ فإن كان على الخادم جدار حماية للاتصالات الخارجة، فاسمح بالمنفذ 443 للخارج، وامنع نطاقات الشبكات الخاصة و`169.254.169.254` (SECURITY_DESIGN §6).
- `BILLING_PROVIDER=paymob` مع إعدادات <span dir="ltr">`PAYMOB_*`</span> (أو `disabled`).
- `SALES_EMAIL` لرابط «تواصل مع المبيعات» في خطة المؤسسات.
- `FILE_SCAN`: ملف الإنتاج يضبطه على `clamav`، فتفحص خدمة `clamav` ملفات الواجبات قبل أن يفتحها أحد (CLASSROOM.md §5). يحدّث ClamAV بصمات الفيروسات بنفسه من `database.clamav.net`: إن كان هناك جدار حماية للاتصالات الخارجة فاسمح بـ HTTPS إليه (أو شغّل نسخة مرآة خاصة). `FILE_SCAN=off` يوقف الفحص، مع استمرار تصغير الصور. خارج Docker Compose، اضبط `FILE_SCAN=clamav` و`CLAMAV_HOST` و`CLAMAV_PORT` (3310) للعامل الخلفي، وشغّل `clamd` بمنفذ TCP لا يصل إليه غيره.
- المساعدة بالذكاء الاصطناعي (اختيارية، docs/AI_LAYER.md): `AI_PROVIDER` (`gemini` أو `anthropic` أو `openai`؛ `none` افتراضيًا)، و`AI_API_KEY` و`AI_MODEL`. استخدم فئة API مدفوعة تنص شروطها على عدم تدريب النماذج على طلباتك. تحقّق من المفتاح والنموذج بالأمر `npm run ai:check` (بالمتغيرات نفسها) قبل تفعيل الذكاء الاصطناعي لأي مدرسة؛ ثم يحدّد مسؤول المنصة حصة شهرية لكل مدرسة. يرسل التطبيق طلبات HTTPS خارجة إلى المزوّد: إن كان هناك جدار حماية للاتصالات الخارجة فاسمح بعنوان واجهته (`generativelanguage.googleapis.com` أو `api.anthropic.com` أو `api.openai.com`).

يرفض التطبيق العمل في الإنتاج مع مزود الدفع التجريبي، أو بريد غير SMTP، أو `APP_URL` لا يبدأ بـ https، أو `FILE_SCAN` غير مضبوط، أو مزوّد ذكاء اصطناعي بلا مفتاحه ونموذجه، أو دور قاعدة بيانات يتجاوز أمان مستوى الصف (RLS).

### 3.3 التشغيل

`ops/start.sh --env prod` (لينكس) أو `ops\start.bat --env prod` (ويندوز) يفحص الإعدادات، ويبني الصورة في المرة الأولى، ويشغّل كل الخدمات، وينتظر حتى يصبح مثيلا التطبيق جاهزين ([القسم 8.2](#82-التشغيل-والإيقاف-والحالة)). وهو يشغّل ما يلي:

<div dir="ltr">

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env.production up -d --build
docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env.production ps
curl -fsS https://<domain>/readyz
```

</div>

يعمل الإنتاج بمثيلين للتطبيق (`app` و`app2`) خلف Caddy، الذي يوزع الطلبات بينهما، ويفحص <span dir="ltr">`/readyz`</span> كل ثانيتين، ويتجنب المثيل الذي يُعاد تشغيله أو المتوقف. يفتح كل مثيل حتى `DATABASE_POOL_MAX` اتصالًا بقاعدة البيانات (10 افتراضيًا): يحتاج المثيلان والعامل الخلفي نحو 21 اتصالًا، وهذا أقل بكثير من الحد الافتراضي لـ PostgreSQL وهو 100 (تحقق من حد الخطة إن كانت قاعدة البيانات مُدارة).

تحتاج خدمة `clamav` (الصورة `clamav/clamav:1.5`، والبصمات محفوظة في المجلد الدائم `clamav_db`) إلى دقيقة أو اثنتين لتحميل البصمات في أول تشغيل، ونحو 15 ثانية بعد ذلك. ملفات الواجبات المرفوعة في هذه الأثناء تنتظر، وتُفحص بمجرد أن يستجيب (ويسجّل العامل الخلفي أنه ينتظر). لا تستمع الخدمة إلا داخل شبكة الخدمات.

يحصل Caddy على شهادات TLS تلقائيًا. سجل كل حاوية محدود بخمسة ملفات حجم كل منها 10 ميجابايت، فلا تملأ السجلات القرص.

**PostgreSQL مُدار.** أنشئ الأدوار الثلاثة بأوامر SQL الموجودة في `deploy/postgres-init/01-roles.sh`، ثم اضبط في <span dir="ltr">`.env.production`</span>:

| الإعداد | القيمة |
| --- | --- |
| `DATABASE_URL` | دور التطبيق (`midad_app`)، مثلًا `postgres://midad_app:…@db.example.com:5432/midad` |
| `MIGRATION_DATABASE_URL` | الدور المالك (`midad_owner`)، قاعدة البيانات نفسها |
| `BACKUP_DATABASE_URL` | دور النسخ الاحتياطي (`midad_backup`، مع `BYPASSRLS` و`pg_read_all_data`)، قاعدة البيانات نفسها |
| `DATABASE_SSL` | `true` |
| `RESTORE_ADMIN_URL` (اختياري) | للاستعادة: دور يستطيع إنشاء قواعد بيانات وعضو في الدور المالك، على قاعدة البيانات `postgres`؛ إن تُرك فارغًا سألت عنه الاستعادة |

عند ضبط `DATABASE_URL` تشغّل السكربتات كل الخدمات ما عدا خدمة `postgres` المضمّنة. إن كان المزود لا يسمح بـ `BYPASSRLS`، فلن تستطيع السكربتات أخذ نسخة احتياطية (جداول المؤسسات تفرض أمان مستوى الصف حتى على مالكها): استخدم حينها النسخ الاحتياطية للمزود والاستعادة إلى نقطة زمنية.

### 3.5 إعداد Paymob (عند توفر بيانات الاعتماد)

0. قبل أي نشر، وبمفاتيح **وضع الاختبار** على جهاز مطوّر:
   `PAYMOB_SECRET_KEY=… PAYMOB_PUBLIC_KEY=… PAYMOB_HMAC_SECRET=… PAYMOB_INTEGRATION_IDS=… npm run paymob:check`.
   ينشئ الأمر عملية دفع تجريبية حقيقية بمحوّل التطبيق نفسه، ويطبع رابط الدفع (ادفع ببطاقة Paymob التجريبية)، ويتحقق من إعادة التوجيه الموقّعة على `localhost`. المفاتيح الحية مرفوضة.
1. أنشئ وسائل الدفع بالبطاقة (والمحفظة) في Paymob، وسجّل أرقامها (integration ids).
2. اضبط عنوان الإشعار بإتمام العملية على `https://<domain>/api/billing/webhooks/paymob`.
3. انسخ المفتاح السري والمفتاح العام وسر HMAC إلى ملف الإعدادات، وأعد تشغيل `app` و`worker`.
4. في وضع الاختبار في Paymob جرّب: اشتراك ← دفع ← تأكد أن الفاتورة أصبحت مدفوعة؛ ثم ارفض عملية دفع؛ وأعد إرسال إشعار؛ وراجع <span dir="ltr">`/admin/events`</span>. سجّل النتائج في TEST_REPORT.md قبل التشغيل الفعلي.

## 4. الترقيات والرجوع إلى الإصدار السابق

1. خذ نسخة احتياطية (`ops/backup.sh --env prod`، وفي ويندوز `ops\backup.bat --env prod`)، ثم `git pull` (أو انتقل إلى إصدار موسوم)، ثم في لينكس `scripts/rolling-restart.sh --build`. يعيد السكربت بناء الصورة، ويطبّق الترحيلات الجديدة والإصدار القديم ما زال يخدم المستخدمين، ثم يستبدل `app` وينتظر جاهزيته، ثم يستبدل `app2`، وأخيرًا العامل الخلفي. ينهي كل مثيل الطلبات الجارية خلال 5 ثوانٍ قبل أن يتوقف، فلا تضيع أي طلبات أثناء إعادة التشغيل (TEST_REPORT §4).
   - بدون <span dir="ltr">`--build`</span> يعيد السكربت تشغيل المثيلين فقط، واحدًا بعد الآخر. إن لم يصبح أحدهما جاهزًا توقف السكربت، واستمر الآخر في الخدمة.
   - في ويندوز (أو كطريق أبسط في لينكس): شغّل `ops\start.bat --env prod` وأجب بنعم (y) على السؤال «<span dir="ltr">Rebuild the app image first</span>» (أعد بناء صورة التطبيق أولًا). يُعاد تشغيل المثيلين معًا، فتنقطع الخدمة بضع ثوانٍ.
2. يجب أن تكون الترحيلات متوافقة مع الإصدار السابق (أضف الأعمدة والجداول أولًا، واحذفها لاحقًا)، حتى لا يحتاج الرجوع إلا إلى الصورة القديمة.
3. الرجوع إلى الإصدار السابق: طريقتا إعادة البناء كلتاهما تحتفظان بالصورة التي تستبدلانها باسم `midad:previous`. أضف `APP_IMAGE_TAG=previous` إلى <span dir="ltr">`.env.production`</span> وشغّل `ops/start.sh --env prod` (أو `APP_IMAGE_TAG=previous scripts/rolling-restart.sh`). احذف هذا السطر قبل الترقية التالية، وإلا بُنيت الصورة الجديدة بهذا الاسم. إن احتاج الأمر إلى التراجع عن ترحيل، فاستعد النسخة الاحتياطية التي أُخذت قبل الترقية ([القسم 8.6](#86-الاستعادة)).

### تغيير مفتاح التشفير `DATA_ENCRYPTION_KEY`

يشفّر هذا المفتاح أسرار التحقق بخطوتين وأسرار توقيع إشعارات الأنظمة الخاصة بالعملاء. غيّره مرة في السنة تقريبًا، وعند مغادرة شخص كان يعرفه، أو إن احتُمل تسرّبه. لا يتوقف التطبيق أثناء ذلك.

1. **خذ نسخة احتياطية أولًا:** شغّل `ops/backup.sh --env prod` ([القسم 8](#8-سكربتات-التشغيل-لينكس-وويندوز)). ثم افحص الوضع الحالي:
   `docker compose … exec app node dist/cli/rotate-data-key.js --check`. يطبع الأمر معرّف المفتاح الحالي (بصمة قصيرة، لا المفتاح نفسه) وعدد القيم المشفرة بكل مفتاح.
2. **بدّل المفاتيح:** ولّد مفتاحًا جديدًا بالأمر `openssl rand -base64 32` (أو أمر PowerShell في [القسم 3.2](#32-الإعدادات)). في <span dir="ltr">`.env.production`</span> انقل المفتاح الحالي إلى `DATA_ENCRYPTION_KEYS_PREVIOUS`، وضع الجديد في `DATA_ENCRYPTION_KEY`.
3. **أعد التشغيل:** شغّل `scripts/rolling-restart.sh`. يكتب كل مثيل الآن بالمفتاح الجديد، ويظل يقرأ القديم.
   - خلال الثواني القليلة لإعادة التشغيل، لا يستطيع مثيل لم يُعَد تشغيله بعد أن يقرأ قيمة كتبها مثيل أُعيد تشغيله للتو، مثل تفعيل جديد للتحقق بخطوتين.
   - الرمز أو الاختبار الذي يفشل في هذه اللحظات يمكن إعادته.
4. **أعد التشفير:** شغّل `docker compose … exec app node dist/cli/rotate-data-key.js`. يعيد الأمر كتابة كل قيمة بالمفتاح الجديد، ويطبع الأعداد لكل عمود، ويسجّل `admin.data_key_rotated` في سجل تدقيق المنصة (الأعداد ومعرّف المفتاح فقط).
   - ينتهي برمز الخروج 1 ويسرد كل قيمة لا يستطيع أي من المفاتيح المضبوطة قراءتها.
   - في هذه الحالة أضف المفتاح الذي كُتبت به تلك القيمة إلى `DATA_ENCRYPTION_KEYS_PREVIOUS` وشغّله مرة أخرى.
5. **تأكد:** يُظهر <span dir="ltr">`--check`</span> كل القيم بالمفتاح الحالي.
6. **احذف المفتاح القديم:** أفرغ `DATA_ENCRYPTION_KEYS_PREVIOUS` وشغّل `scripts/rolling-restart.sh` مرة أخرى.
7. **احتفظ بالمفتاح القديم مع النسخ الاحتياطية القديمة:** احفظه بعيدًا عن النسخ الاحتياطية، ما دمت تحتفظ بنسخ أُخذت قبل الخطوة 4. استعادة أي منها تحتاجه: أعده إلى `DATA_ENCRYPTION_KEYS_PREVIOUS`، ونفّذ الخطوة 4 على قاعدة البيانات المستعادة، ثم احذفه مرة أخرى. أتلف المفتاح القديم عند حذف آخر تلك النسخ.

محليًا: `npm run keys:check` و`npm run keys:rotate`.

## 5. النسخ الاحتياطي والاستعادة

استخدم سكربتات التشغيل ([القسم 8](#8-سكربتات-التشغيل-لينكس-وويندوز)): `ops/backup.sh` أو `ops\backup.bat` للنسخ الاحتياطي (مشفّرًا، مع نسخ إلى مجلد أو قرص USB أو خادم آخر أو مخزن سحابي)، و`ops/restore.sh --only-verify` لاختبار نسخة، و`ops/restore.sh` للاستعادة، و[القسم 8.8](#88-إعادة-بناء-خادم-مفقود) لإعادة بناء خادم مفقود. الحد الأدنى:

- **نسخة احتياطية يومية مجدولة**، مع نسخة واحدة على الأقل **خارج الخادم** ([القسم 8.5](#85-النسخ-والاختبار-المجدولان))؛
- **اختبار أسبوعي** لأحدث نسخة خارج الخادم ([القسم 8.5](#85-النسخ-والاختبار-المجدولان))، وتجربة استعادة كاملة قبل الإطلاق وبعد كل تغيير كبير؛
- عبارة مرور النسخ الاحتياطية و<span dir="ltr">`.env.production`</span> (وأهم ما فيه `DATA_ENCRYPTION_KEY`) محفوظان في مدير كلمات مرور، بعيدًا عن النسخ الاحتياطية.

احتفظ بثلاثين نسخة يومية على الأقل (وهي مدة الحفظ الافتراضية) واثنتي عشرة نسخة شهرية **(افتراض)**: للنسخ الشهرية احفظ نسخة كل شهر في مكان لا يحذف منه السكربت (مجلد ثانٍ، أو مخزن سحابي مع حفظ الإصدارات)، لأن السكربتات تحذف حسب العمر فقط.

السكربتات الأقدم `scripts/backup.sh` و`scripts/verify-backup.sh` و`scripts/restore.sh` تعمل مع أي PostgreSQL يصل إليه الخادم وعليه أدوات عميل PostgreSQL (بدون Docker)؛ وهي تتعامل مع قاعدة البيانات فقط، لا مع الإعدادات ولا الشهادات ولا النسخ الإضافية.

الأهداف **(افتراض)**: أقصى فقد للبيانات (RPO) 24 ساعة مع النسخ اليومية (دقائق مع الاستعادة إلى نقطة زمنية في قاعدة بيانات مُدارة)، وأقصى مدة للتوقف (RTO) 4 ساعات. في التجربة أُعيد بناء خادم مُسح بالكامل من نسخة خارجه في نحو 90 ثانية من وقت تشغيل السكربت (TEST_REPORT §4).

## 6. المراقبة والتنبيهات

**مضمّنة في التطبيق (اضبطها قبل الإطلاق).** اضبط `ALERT_EMAILS` (عناوين مفصولة بفواصل) و/أو `ALERT_WEBHOOK_URL` (رابط إشعارات واردة في Slack أو Discord أو Mattermost، أو أي عنوان يقبل JSON) في <span dir="ltr">`.env.production`</span>، ثم استخدم إدارة المنصة ← نظرة عامة ← **إرسال تنبيه تجريبي** للتأكد من الوصول. عامل رابط الإشعارات معاملة السر. يفحص كل مثيل مرة في الدقيقة؛ تُرسل رسالة واحدة عند بدء المشكلة، وتذكير كل 6 ساعات ما دامت مستمرة، ورسالة عند زوالها لمدة 5 دقائق. تُرسل التنبيهات مباشرة (لا عبر طابور البريد)، وتُكتب أيضًا في السجلات (<span dir="ltr">`"msg":"operational alert"`</span>)، ولا تحتوي إلا على أعداد.

| التنبيه | متى يصدر | أول ما تفحصه |
| --- | --- | --- |
| توقف العامل الخلفي | لا نبض من العامل الخلفي منذ دقيقتين (4 × `WORKER_INTERVAL_MS`) | `docker compose … ps worker` و`logs worker` |
| فشل رسائل البريد | رسالة استُسلم في إرسالها خلال الساعة الأخيرة، أو 3 رسائل أو أكثر قيد إعادة المحاولة | إعدادات SMTP والمزود؛ سجلات العامل الخلفي |
| تأخر البريد | رسالة تنتظر منذ أكثر من 15 دقيقة | هل العامل الخلفي يعمل |
| أخطاء الخادم | 10 ردود أو أكثر بحالة 500–599 خلال 5 دقائق على مثيل واحد | `docker compose … logs app app2` |
| فشل إشعارات الدفع | فشلت معالجة إشعار من مزود الدفع خلال الساعة الأخيرة | إدارة المنصة ← إشعارات الأنظمة |
| ترحيلات معلّقة | بنية قاعدة البيانات أقدم من الكود | `docker compose … run --rm migrate` |
| ملفات واجبات تنتظر | ملف واجب ينتظر فحصه (فحص الفيروسات، تصغير الصور) منذ أكثر من 10 دقائق، ولا يستطيع أحد فتحه في هذه الأثناء | `docker compose … ps clamav worker` و`logs clamav worker` (يسجّل العامل الخلفي خطأ الفاحص) |
| تعذّر الوصول إلى قاعدة البيانات | فحصان متتاليان لا يصلان إلى PostgreSQL (رسالة من كل مثيل) | `ps postgres` أو حالة قاعدة البيانات المُدارة |

**من خارج الخادم (مطلوب أيضًا).** لا يستطيع شيء على الخادم أن يبلّغ عن توقف الخادم نفسه أو Caddy أو مثيلي التطبيق معًا. أضف فحص توافر خارجيًا للعنوان `https://<domain>/readyz` كل دقيقة، ينبّه بعد فشلين (أي خدمة لمراقبة التوافر، مثل UptimeRobot أو Better Stack)؛ وهو يغطي أيضًا انتهاء صلاحية شهادة TLS.

| إشارة أخرى | كيف |
| --- | --- |
| السجلات | سجلات JSON من `app` و`app2` و`worker` (`docker compose logs`)؛ أرسلها إلى خدمة سجلات للبحث فيها وحفظها |
| حجم القرص وقاعدة البيانات | مراقبة الخادم؛ `pg_database_size` في PostgreSQL |
| النسخ الاحتياطية | رسالة الفشل من مهمة النسخ المجدولة أو خدمة السجلات؛ تجربة الاستعادة ([القسم 5](#5-النسخ-الاحتياطي-والاستعادة)) |

## 8. سكربتات التشغيل (لينكس وويندوز)

يحتوي <span dir="ltr">`ops/`</span> على أداة واحدة بشكلين: `ops/midad.sh` للينكس (bash)، و`ops\midad.ps1` لويندوز (PowerShell)، ومعهما ملفات تشغيل قصيرة. يقوم الشكلان بالأعمال نفسها، ويقرآن الإعدادات نفسها، ويصنعان النسخ الاحتياطية نفسها: النسخة التي يصنعها أحدهما يستعيدها الآخر. لا يحتاج الجهاز إلا إلى Docker مع Compose v2؛ أما أدوات قاعدة البيانات والتشفير ونقل الملفات فتعمل داخل حاويات.

**رسائل السكربتات وأسئلتها بالإنجليزية.** يذكر هذا الدليل نص كل سؤال مهم كما يظهر، ومعه شرحه. الإجابة على أسئلة نعم/لا بالحرف `y` (نعم) أو `n` (لا)، وعلى أسئلة الاختيار برقم الخيار. والقيمة بين القوسين المربعين <span dir="ltr">`[ ]`</span> هي الإجابة الافتراضية: اضغط Enter لقبولها.

| المهمة | لينكس | ويندوز |
| --- | --- | --- |
| قائمة بكل ما يلي | `ops/midad.sh` | انقر نقرًا مزدوجًا على `ops\midad.bat` |
| التشغيل | `ops/start.sh` | `ops\start.bat` |
| الإيقاف | `ops/stop.sh` | `ops\stop.bat` |
| الحالة | `ops/status.sh` | `ops\status.bat` |
| النسخ الاحتياطي | `ops/backup.sh` | `ops\backup.bat` |
| الاستعادة | `ops/restore.sh` | `ops\restore.bat` |
| اختبار نسخة احتياطية (لا يغيّر شيئًا) | `ops/restore.sh --only-verify` | `ops\restore.bat --only-verify` |
| إعداد أماكن النسخ الإضافية | `ops/midad.sh destinations` | `ops\midad.bat destinations` |

بدون خيارات تسأل السكربتات عما تحتاجه: أي تثبيت، وأي اختيارات، وأي نسخة احتياطية. وهذه خيارات تعطي الإجابات نفسها مسبقًا، وهي واحدة في النظامين:

| الخيار | المعنى |
| --- | --- |
| <span dir="ltr">`--env dev`</span> أو <span dir="ltr">`--env prod`</span> | بيئة التطوير (`docker-compose.yml` و<span dir="ltr">`.env.docker`</span>) أو الإنتاج (مع `docker-compose.prod.yml` و<span dir="ltr">`.env.production`</span>) |
| <span dir="ltr">`--env-file FILE`</span> | ملف إعدادات آخر |
| <span dir="ltr">`--yes`</span> | لا أسئلة: تُستخدم الاختيارات المحفوظة والقيم الافتراضية (للمهام المجدولة)؛ يحتاج إلى <span dir="ltr">`--env`</span> |
| <span dir="ltr">`--to folder,server,bucket`</span> أو <span dir="ltr">`--to none`</span> | النسخ الاحتياطي: أين تُنسخ النسخة، إضافة إلى مجلد النسخ الاحتياطية |
| <span dir="ltr">`--no-encrypt`</span> | النسخ الاحتياطي: ترك الأرشيف بلا تشفير (غير ممكن إن كان فيه ملف الإعدادات) |
| <span dir="ltr">`--from local\|folder\|server\|bucket`</span> و<span dir="ltr">`--file NAME`</span> | الاستعادة: من أين، وأي نسخة (الافتراضي: الأحدث) |
| <span dir="ltr">`--only-verify`</span> | الاستعادة: اختبار النسخة في قاعدة بيانات مؤقتة فقط |

### 8.1 تجهيز الجهاز

**لينكس** (الموصى به للخادم): Docker Engine مع إضافة Compose (<span dir="ltr">`https://docs.docker.com/engine/install/`</span>)، ثم `systemctl enable docker`، والمستودع في مجلد مثل <span dir="ltr">`/opt/midad`</span>، و<span dir="ltr">`.env.production`</span> ([القسم 3.2](#32-الإعدادات)) لا يقرؤه إلا مالكه (`chmod 600`؛ ويعرض سكربت التشغيل إصلاح ذلك). شغّل السكربتات بصفة root أو بمستخدم عضو في مجموعة `docker`.

**ويندوز 10 (22H2) أو 11:** Docker Desktop بمحرك WSL 2، والمستودع (عبر Git for Windows، أو ملف ZIP من GitHub). تشغّل ملفات <span dir="ltr">`.bat`</span> الملف `ops\midad.ps1` بـ PowerShell 7 إن كان مثبتًا، وإلا بـ Windows PowerShell 5.1 المضمّن في ويندوز، مع السماح بتشغيل هذا السكربت وحده (<span dir="ltr">`-ExecutionPolicy Bypass`</span>). عدّل ملفات الإعدادات بالمفكرة (Notepad).
- لا يعمل Docker Desktop إلا والمستخدم الذي ثبّته مسجّل الدخول: ليعود التطبيق بعد إعادة تشغيل الجهاز، فعّل في إعدادات Docker Desktop الخيار *Start Docker Desktop when you sign in* (تشغيل Docker Desktop عند تسجيل الدخول)، وأبقِ ذلك المستخدم مسجّل الدخول (الشاشة المقفلة لا تمنع ذلك).
- الخادم الذي يجب أن يعمل دون أن يسجّل أحد دخوله مكانه لينكس.
- راجع شروط ترخيص Docker Desktop لمؤسستك (المؤسسات الأكبر تحتاج اشتراكًا مدفوعًا).

**بعد إعادة تشغيل الجهاز** تعود الحاويات وحدها (`restart: unless-stopped`)، إلا إن أُوقفت بسكربت الإيقاف، فتبقى متوقفة.

### 8.2 التشغيل والإيقاف والحالة

- **التشغيل** (start):
  - يفحص ملف الإعدادات: القيم المطلوبة موجودة، ولم تبقَ قيم `change-me`، و<span dir="ltr">`https://`</span> في الإنتاج، والملف لا يقرؤه غيرك.
  - يبني صورة التطبيق في المرة الأولى، ويشغّل كل الخدمات، وينتظر حتى يرد مثيلا التطبيق على <span dir="ltr">`/readyz`</span>، ثم يعرض الحالة.
  - يسأل «<span dir="ltr">Rebuild the app image first (after updating the code)?</span>» أي: هل يعيد بناء الصورة أولًا (بعد تحديث الكود)؟ وتُحفظ الصورة المستبدلة باسم `midad:previous` ([القسم 4](#4-الترقيات-والرجوع-إلى-الإصدار-السابق)).
  - مع قاعدة بيانات مُدارة (`DATABASE_URL` مضبوط) لا تُشغَّل خدمة `postgres` المضمّنة.
- **الإيقاف** (stop) يسأل «<span dir="ltr">Stop how?</span>» (كيف يوقف): الخيار 1 إيقاف مع بقاء الحاويات (ثم التشغيل من جديد بسكربت التشغيل)، أو الخيار 2 إيقاف مع حذف الحاويات. لا يحذف أي منهما بيانات: قاعدة البيانات والشهادات وبصمات الفيروسات تبقى في مجلدات Docker الدائمة.
- **الحالة** (status) تسرد الخدمات مع حالتها وصحتها، وهل كل مثيل للتطبيق جاهز، والعنوان.

### 8.3 النسخ الاحتياطية

| الجزء | في النسخة الاحتياطية |
| --- | --- |
| قاعدة البيانات (`pg_dump`) | دائمًا: كل بيانات المدارس، ومنها ملفات الواجبات والصور (فهي محفوظة داخل قاعدة البيانات) |
| فحص قاعدة البيانات أثناء العمل | دائمًا: الترحيلات، وأمان مستوى الصف، وعدد الصفوف في كل جدول، للمقارنة بعد الاستعادة |
| ملف الإعدادات (<span dir="ltr">`.env.production`</span>) | يُسأل عنه، والافتراضي لا: كلمات المرور والمفاتيح ومنها `DATA_ENCRYPTION_KEY`، وهو لازم لإعادة بناء خادم مفقود؛ ومعه يُشفَّر الأرشيف دائمًا |
| شهادات TLS (Caddy) | يُسأل عنها في الإنتاج، والافتراضي نعم: الخادم المعاد بناؤه يقدّم HTTPS فورًا، دون انتظار شهادات جديدة |

ليس في النسخة: صور Docker (تُبنى من الكود من جديد، والنسخة تسجّل إصدار التطبيق)، وبصمات الفيروسات (تُنزَّل من جديد)، والملف <span dir="ltr">`.env.backup`</span> الذي فيه إعدادات أماكن النسخ (دوّنها في مكان آخر).

- **الاسم والصيغة:** `midad-backup-<dev|prod>-<UTC time>.tar.enc`، والوقت بالتوقيت العالمي (أو <span dir="ltr">`.tar`</span>)، وبجانبه ملف بصمة التحقق <span dir="ltr">`.sha256`</span>؛ وداخله `manifest.txt` يسرد كل جزء ببصمته.
- **التشفير** (مفعّل افتراضيًا): AES-256-GCM بمفتاح مشتق من عبارة المرور (scrypt). تحتاج عبارة المرور إلى 12 حرفًا أو أكثر. تُكتشف عبارة المرور الخاطئة وأي بايت متغيّر. **بدون عبارة المرور لا يمكن فتح النسخة الاحتياطية**: احفظها في مدير كلمات مرور، بعيدًا عن النسخ الاحتياطية. لا تكتبها السكربتات في أي مكان إلا في ملف عبارة المرور الذي تنشئه أنت للمهام المجدولة ([القسم 8.5](#85-النسخ-والاختبار-المجدولان)).
- **أين:** مجلد النسخ الاحتياطية (افتراضيًا <span dir="ltr">`backups/`</span> داخل مجلد المشروع، ولا يقرؤه غيرك؛ ويمكن تغييره بـ `BACKUP_DIR` في <span dir="ltr">`.env.backup`</span>)، والنسخ الإضافية التي تختارها ([القسم 8.4](#84-النسخ-الإضافية-مجلد-أو-قرص-usb-أو-خادم-آخر-أو-مخزن-سحابي)). كل نسخة إضافية تُقارن ببصمتها بعد النقل.
- **النسخ القديمة:** تُحذف النسخ الأقدم من عدد الأيام الذي تختاره (الافتراضي 30، و0 يحتفظ بالكل) من مجلد النسخ الاحتياطية، ومن كل مكان وصلت إليه النسخة الجديدة. لا يُمس إلا الملفات التي يبدأ اسمها بـ <span dir="ltr">`midad-backup-`</span>، ولا يحدث الحذف إلا بعد نسخ ناجح، فتبقى الأحدث دائمًا.
- **الأمان:**
  - يعمل النسخ والتطبيق يخدم المستخدمين (`pg_dump` يقرأ لقطة متسقة).
  - لا يعمل إلا نسخ أو استعادة واحدة في الوقت نفسه. القفل الذي تركه تشغيل أُوقف قسرًا يُتولّى تلقائيًا، ويُحذف ما تركه وراءه (وقد يكون فيه بيانات مفكوكة التشفير).
  - إن فشلت نسخة إضافية، يذكر السكربت أيها، ويحتفظ بالنسخة الاحتياطية، وينتهي برمز خطأ لتبلّغ عنه المهمة المجدولة.
- تُحفظ الاختيارات في <span dir="ltr">`.env.backup`</span> (لا يقرؤه غيرك)، وتُستخدم في المرة التالية ومع <span dir="ltr">`--yes`</span>.

أسئلة النسخ الاحتياطي، بالترتيب الذي تظهر به:

| السؤال كما يظهر | معناه |
| --- | --- |
| `Include the settings file (…)? Needed to rebuild a lost server` | هل يضم ملف الإعدادات؟ لازم لإعادة بناء خادم مفقود |
| <span dir="ltr">`Encrypt the archive with a passphrase (recommended: it holds students' data)?`</span> | هل يشفّر الأرشيف بعبارة مرور؟ (موصى به: فيه بيانات الطلاب). لا يُسأل إن ضُم ملف الإعدادات، فالتشفير حينها إلزامي |
| <span dir="ltr">`Include the TLS certificates (Caddy)?`</span> | هل يضم شهادات TLS؟ (في الإنتاج فقط) |
| `Copy this backup to … Numbers separated by commas, or 0 for none` | إلى أين يُنسخ: 1 مجلد أو قرص USB، و2 خادم آخر، و3 مخزن سحابي؛ أرقام مفصولة بفواصل، أو 0 لا شيء |
| <span dir="ltr">`Use this choice by default next time?`</span> | هل يكون هذا الاختيار هو الافتراضي في المرة القادمة؟ |
| <span dir="ltr">`Delete backups older than how many days, here and in the copies (0 = keep all)`</span> | حذف النسخ الأقدم من كم يومًا، هنا وفي النسخ الإضافية (0 = الاحتفاظ بالكل) |
| <span dir="ltr">`Backup passphrase …`</span> ثم `Type it again` | عبارة المرور، ثم إعادة كتابتها |

### 8.4 النسخ الإضافية: مجلد أو قرص USB أو خادم آخر أو مخزن سحابي

احتفظ بنسخة واحدة على الأقل **خارج الخادم**. أعدّ أماكن النسخ من القائمة («<span dir="ltr">Set up backup copies</span>»)، أو عندما يطلبها النسخ الاحتياطي لأول مرة؛ ويُختبر الاتصال عند الحفظ.

| المكان | ما تعطيه | ملاحظات |
| --- | --- | --- |
| مجلد أو قرص USB | مسار: قرص موصول، أو مجلد مشترك على الشبكة (في ويندوز: محرك شبكة معيّن أو <span dir="ltr">`\\server\share\folder`</span>) | يجب أن يكون القرص موصولًا وقت النسخ |
| خادم آخر (SFTP) | العنوان، والمنفذ، والمستخدم، والمجلد؛ وملف مفتاح SSH (موصى به) أو كلمة مرور؛ وملف `known_hosts` | اتصل مرة أولًا بالأمر `ssh user@host` ليُحفظ مفتاح الخادم في <span dir="ltr">`~/.ssh/known_hosts`</span> (في ويندوز: <span dir="ltr">`%USERPROFILE%\.ssh\known_hosts`</span>، بعميل OpenSSH المضمّن في ويندوز). إن تغيّر مفتاح الخادم توقف النسخ حتى تتحقق من السبب وتحدّث الملف. لاستخدام كلمة مرور بدل مفتاح محفوظ، أجب `none` على سؤال ملف المفتاح. تُحفظ كلمة المرور مموّهة لا مشفّرة: أبقِ <span dir="ltr">`.env.backup`</span> خاصًا |
| مخزن سحابي متوافق مع S3 (bucket) | عنوان الخدمة (endpoint: فارغ لـ Amazon S3؛ ومثلًا `s3.eu-central-003.backblazeb2.com` و<span dir="ltr">`<account>.r2.cloudflarestorage.com`</span> و`s3.eu-central-1.wasabisys.com`)، والمنطقة، واسم المخزن، والمجلد داخله، ومفتاح الوصول | يحتاج المفتاح إلى صلاحيات السرد والقراءة والكتابة والحذف في ذلك المخزن (الحذف للنسخ القديمة). لنسخ لا يستطيع هذا الخادم حذفها، استخدم قفل الكائنات (object lock) أو حفظ الإصدارات (versioning) لدى المزود، بمدة حفظ يحددها المزود |

مرجع إعدادات <span dir="ltr">`.env.backup`</span> (تكتبها القائمة؛ لا تعدّل يدويًا إلا الأسطر المتقدمة):

| الإعداد | المعنى |
| --- | --- |
| `BACKUP_DIR` | مجلد النسخ الاحتياطية (الافتراضي <span dir="ltr">`backups/`</span> في المشروع) |
| `BACKUP_COPY_TO` | أماكن النسخ الافتراضية، مثلًا `folder,bucket` |
| `BACKUP_KEEP_DAYS` | حذف النسخ الأقدم من هذا العدد من الأيام (0 = أبدًا) |
| `BACKUP_ENCRYPT` و`BACKUP_INCLUDE_SETTINGS` و`BACKUP_INCLUDE_CERTIFICATES` | الإجابات المحفوظة (`yes` أو `no`) |
| `BACKUP_PASSPHRASE_FILE` | ملف فيه عبارة المرور، للمهام المجدولة ([القسم 8.5](#85-النسخ-والاختبار-المجدولان)) |
| `BACKUP_FOLDER`؛ <span dir="ltr">`BACKUP_SERVER_*`</span>؛ <span dir="ltr">`BACKUP_BUCKET_*`</span> | أنواع النسخ الثلاثة |
| `BACKUP_DOCKER_NETWORK` | متقدم: شبكة Docker تنضم إليها حاويات الأدوات، لخادم نسخ أو قاعدة بيانات لا يُوصل إليهما إلا عبرها |
| `BACKUP_PG_IMAGE` | متقدم، لقاعدة بيانات مُدارة: أدوات عميل بإصدار لا يقل عن إصدار الخادم، مثلًا `postgres:17-alpine` لـ PostgreSQL 17 |

### 8.5 النسخ والاختبار المجدولان

شغّل أولًا نسخًا احتياطيًا واحدًا يدويًا وأجب على الأسئلة: المهمة المجدولة (<span dir="ltr">`--yes`</span>) تعيد استخدام تلك الإجابات. ولعبارة المرور، اختر من قائمة أماكن النسخ «<span dir="ltr">Passphrase file for scheduled backups</span>» (ملف عبارة المرور للنسخ المجدول): يكتب عبارة المرور في ملف لا يقرؤه غيرك (وفي ويندوز: أنت وحساب SYSTEM)، ويحفظ مكانه. أو اضبط `MIDAD_BACKUP_PASSPHRASE` في بيئة المهمة المجدولة.

**لينكس (cron):**

<div dir="ltr">

```bash
# /etc/cron.d/midad   (cron emails the echo line when a run fails)
MAILTO=ops@example.com
15 2 * * * root cd /opt/midad && ops/backup.sh --env prod --yes >>/var/log/midad-backup.log 2>&1 || echo "Midad backup failed: see /var/log/midad-backup.log"
45 3 * * 0 root cd /opt/midad && ops/restore.sh --env prod --yes --from bucket --only-verify >>/var/log/midad-backup.log 2>&1 || echo "Midad backup test failed: see /var/log/midad-backup.log"
```

</div>

السطر الأول نسخ يومي في الساعة 02:15، ويرسل cron رسالة إلى `MAILTO` إن فشل. والسطر الثاني يختبر أحدث نسخة في المخزن السحابي كل يوم أحد (استخدم `server` أو `folder` لتلك الأماكن).

**ويندوز (Task Scheduler، برنامج جدولة المهام):**
1. اختر «<span dir="ltr">Create Task…</span>» (إنشاء مهمة).
2. اختر «<span dir="ltr">Run only when user is logged on</span>» (التشغيل فقط عند تسجيل دخول المستخدم)، لأن Docker Desktop يحتاج المستخدم مسجّل الدخول.
3. المشغّل (Trigger): يوميًا (Daily) في الساعة 02:15.
4. الإجراء «<span dir="ltr">Start a program</span>» (تشغيل برنامج):
   - البرنامج: `cmd.exe`
   - الوسائط: <span dir="ltr">`/c ops\backup.bat --env prod --yes >> backups\backup-log.txt 2>&1`</span>
   - «<span dir="ltr">Start in</span>» (البدء في): مجلد المشروع، مثلًا `C:\midad`.
5. مهمة ثانية، أسبوعية، بالأمر `ops\restore.bat --env prod --yes --from bucket --only-verify`.

يُظهر عمود «<span dir="ltr">Last Run Result</span>» (نتيجة آخر تشغيل) القيمة `0x0` للنجاح و`0x1` للفشل، والتفاصيل في ملف السجل.

لا تجدول استعادة بدون <span dir="ltr">`--only-verify`</span> أبدًا: مع <span dir="ltr">`--yes`</span> ستنقل التطبيق إلى البيانات المستعادة.

### 8.6 الاستعادة

تسأل الاستعادة «<span dir="ltr">Restore from where?</span>» (من أين: مجلد النسخ الاحتياطية أو أحد أماكن النسخ) و«<span dir="ltr">Which backup? (newest first)</span>» (أي نسخة، والأحدث أولًا)، ثم:

1. تجلبها، وتتحقق من بصمتها، وتفك تشفيرها، وتطابق كل جزء مع قائمة المحتويات.
2. **ملف الإعدادات** (إن كان في النسخة): تسأل «<span dir="ltr">Restore the settings file over …?</span>» هل تضعه مكان الملف الحالي (الذي يُحفظ باسمه مضافًا إليه <span dir="ltr">`.before-restore-<time>`</span>، أي الوقت). وعلى جهاز ليس عليه ملف إعدادات يُعاد دون سؤال.
3. تستعيد قاعدة البيانات في **قاعدة بيانات جديدة** باسم <span dir="ltr">`<name>_r<time>`</span> (اسم قاعدة البيانات الحالية ثم الوقت)؛ ولا تُمس قاعدة البيانات الحالية. وتسأل قبل ذلك «<span dir="ltr">Go ahead?</span>» (هل تتابع؟).
4. تفحصها: الترحيلات نفسها، وأمان مستوى الصف ما زال مفروضًا على كل جدول، وعدد صفوف كل جدول مقارنًا بالفحص الذي أُجري وقت النسخ. تُسرد الفروق، والتغييرات التي حدثت أثناء النسخ تسبب فروقًا صغيرة.
5. **الشهادات** (إن كانت في النسخة): تسأل «<span dir="ltr">Restore the TLS certificates too?</span>»، وتُحفظ الشهادات الحالية أولًا باسم <span dir="ltr">`backups/caddy-data-before-restore-<time>.tar.gz`</span>.
6. **التحويل** عند موافقتك على «<span dir="ltr">Switch the app to … now?</span>» (نحو دقيقة بلا خدمة):
   - توقف التطبيق والعامل الخلفي، وتحفظ الإعدادات الحالية باسم الملف مضافًا إليه <span dir="ltr">`.before-switch-<time>`</span>.
   - تضبط `DB_NAME` على قاعدة البيانات الجديدة (ومع قاعدة بيانات مُدارة: اسم قاعدة البيانات في العناوين الثلاثة).
   - تشغّل كل شيء، وتنتظر الجاهزية، ثم تتأكد أن `DATA_ENCRYPTION_KEY` يقرأ كل سر محفوظ (أسرار التحقق بخطوتين وإشعارات الأنظمة).

كل ما كُتب بعد أخذ النسخة ليس في قاعدة البيانات المستعادة. قاعدة البيانات السابقة تبقى، ويطبع السكربت أمر حذفها حين لا تحتاج إليها.
- **للتراجع عن استعادة:** انسخ الملف الذي ينتهي اسمه بـ <span dir="ltr">`.before-switch-<time>`</span> فوق ملف الإعدادات، وشغّل سكربت التشغيل.
- **إن فشل فحص المفتاح:** استعد ملف الإعدادات من النسخة نفسها، أو ضع المفتاح الذي أُخذت به النسخة في `DATA_ENCRYPTION_KEYS_PREVIOUS` ([القسم 4](#4-الترقيات-والرجوع-إلى-الإصدار-السابق)، تغيير المفتاح).

### 8.7 اختبار نسخة احتياطية

«<span dir="ltr">Test a backup</span>» (اختبار نسخة، أو <span dir="ltr">`--only-verify`</span>) ينفّذ الخطوة 1 والخطوتين 3 و4 في قاعدة بيانات مؤقتة، ثم يحذفها. لا يتغير شيء آخر، ويستمر التطبيق في العمل. اختبر أحدث نسخة خارج الخادم كل أسبوع ([القسم 8.5](#85-النسخ-والاختبار-المجدولان))، وبعد تغيير إعدادات أماكن النسخ.

### 8.8 إعادة بناء خادم مفقود

1. جهّز الجهاز الجديد ([القسم 8.1](#81-تجهيز-الجهاز)) واحصل على الكود: بالإصدار نفسه الذي أُخذت به النسخة أو أحدث. تعرض الاستعادة الإصدار الذي صُنعت به النسخة، والكود الأحدث يرقّي قاعدة البيانات المستعادة عند التشغيل.
2. أحضر ما يوصل إلى مكان النسخة (قرص USB؛ أو مفتاح SSH و`known_hosts`؛ أو مفتاح الوصول إلى المخزن السحابي)، وعبارة المرور.
3. شغّل `ops/restore.sh --env prod` (في ويندوز `ops\restore.bat --env prod`)، واختر المكان (يسأل عن إعدادات الاتصال)، ثم النسخة، ثم عبارة المرور. إن لم يكن على الجهاز <span dir="ltr">`.env.production`</span> أعيد ملف الإعدادات من النسخة؛ ثم تتبعه قاعدة البيانات والشهادات ويبدأ التطبيق.
4. إن تغيّر عنوان الخادم فحدّث DNS. ثم أعدّ أماكن النسخ والمهام المجدولة من جديد (<span dir="ltr">`.env.backup`</span> ليس في النسخ الاحتياطية).

نسخة ليس فيها ملف الإعدادات تحتاج إلى كتابة <span dir="ltr">`.env.production`</span> أولًا، بقيمة `DATA_ENCRYPTION_KEY` نفسها (لا يمكن قراءة أسرار التحقق بخطوتين وإشعارات الأنظمة بدونها). أما كلمات مرور قاعدة البيانات فلا بأس أن تكون جديدة مع قاعدة البيانات المضمّنة، التي تنشئ أدوارها عند أول تشغيل. و`SESSION_SECRET` الجديد يُخرج الجميع، فيسجّلون الدخول من جديد.

### 8.9 مع قاعدة بيانات مُدارة

عند ضبط `DATABASE_URL` ([القسم 3.3](#33-التشغيل)):
- يقرأ النسخ الاحتياطي قاعدة البيانات عبر `BACKUP_DATABASE_URL`.
- تنشئ الاستعادة قاعدة البيانات الجديدة على الخادم المُدار عبر `RESTORE_ADMIN_URL` (من ملف الإعدادات، أو تسأل عنه)، وتفحصها بدور النسخ الاحتياطي، وتغيّر العناوين الثلاثة.
- يحتاج دور المدير إلى صلاحية إنشاء قواعد البيانات وعضوية الدور المالك (<span dir="ltr">`GRANT midad_owner TO <admin>`</span>)، ولا يحتاج إلى صلاحيات superuser.

### 8.10 ما الذي جُرِّب

شغّلت التجربة المسجّلة في TEST_REPORT §4 السكربتين على مجموعة خدمات الإنتاج بمثيلين للتطبيق وClamAV. احتوت البيانات على مدرسة فيها اختبار إلكتروني لعشرين طالبًا، ومالك مفعّل التحقق بخطوتين، وإشعار أنظمة (سرّه محفوظ مشفّرًا)، وصورة واجب.
- **أماكن النسخ:** حاويات: خادم SFTP (بمفتاح وبكلمة مرور)، وخادم متوافق مع S3، ومجلد.
- **قاعدة البيانات المُدارة:** جُرّبت على PostgreSQL منفصل بمدير ليس superuser.
- **سكربت ويندوز:** شُغّل بـ PowerShell 7.4 على لينكس، و**لم يُشغَّل بعد على ويندوز** (Docker Desktop وWindows PowerShell 5.1 و`cmd.exe`). قبل الاعتماد عليه، خذ نسخة واحدة واختبرها واستعدها على جهاز ويندوز نفسه.
